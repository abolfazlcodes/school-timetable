# معماری اطلاعات ساده‌شده فاز یک

## اصل طراحی

مدل دامنه و موتور زمان‌بندی غنی باقی می‌مانند، اما UI بازتاب مستقیم جدول‌های پایگاه‌داده نیست. کاربر با پنج مقصد روشن و یک جریان اصلی روبه‌رو می‌شود. صفحه جدید تنها زمانی ساخته می‌شود که یک کار مستقل و پرتکرار داشته باشد.

## ناوبری اصلی

| مقصد | مسئولیت UI | موارد ادغام‌شده |
|---|---|---|
| داشبورد | خلاصه کوچک و اقدام «ادامه برنامه‌ریزی» | سال فعال، تعداد کلاس/دبیر/ساعت، وضعیت برنامه، موارد مهم |
| برنامه‌ریزی | جریان هدایت‌شده آماده‌سازی تا انتشار | سال، پایه، رشته، کلاس، درس، curriculum، حضور، preflight، generation و انتشار |
| دبیران | workspace واحد فهرست و جزئیات دبیر | مشخصات، درس‌ها، workload، محدودیت و grid حضور |
| برنامه هفتگی | workspace نهایی مشاهده و اصلاح | نمای کلاس/دبیر، conflict و warning زمینه‌ای، نسخه‌ها، چاپ و export |
| تنظیمات | حداقل تنظیمات مدرسه | نام مدرسه، روزهای کاری و زنگ‌ها در صورتی که در جریان برنامه‌ریزی مناسب نباشند |

Validation، conflict، availability، schedule run، version و export مقصد مستقل منو نیستند.

## جریان برنامه‌ریزی

یک route و یک stepper هفت‌مرحله‌ای استفاده می‌شود. تغییر مرحله context کاربر و داده واردشده را حفظ می‌کند:

1. ساختار مدرسه — سال، پایه، رشته، کلاس، دانش‌آموز و پیشنهاد تعداد کلاس
2. دروس و ساعات — درس، ساعت هفتگی، تعداد/الگوی جلسه و مجموع workload
3. دبیران و حضور — انتخاب/ایجاد دبیر، assignment، workload و grid حضور در همان context
4. بررسی اطلاعات — preflight فشرده با اقدام مستقیم برای اصلاح هر issue
5. تولید برنامه — یک اقدام اصلی، پیشرفت و نتیجه قابل‌فهم بدون اصطلاحات solver
6. بررسی و اصلاح — ورود به همان timetable workspace با validation زمینه‌ای
7. انتشار — خلاصه نهایی، تأیید و ایجاد نسخه منتشرشده

مرحله‌ها صفحه top-level جدا ندارند. URL می‌تواند مرحله فعلی را برای refresh/bookmark نگه دارد، اما پوسته، داده موقت و ناوبری یکپارچه است.

مسیر `/planning` هر هفت گام را در همان پوسته نمایش می‌دهد. `/planning?step=edit` و `/planning?step=publish` همان workspace مسیر `/timetable` را بازاستفاده می‌کنند و کنترل‌های انتشار از همان toolbar در دسترس‌اند. روزها و زنگ‌ها داخل گام ساختار قرار گرفته‌اند تا کاربر برای آماده‌سازی ورودی‌ها به تنظیمات رفت‌وبرگشت نکند.

## workspace دبیران

در desktop فهرست فشرده در کنار detail panel نمایش داده می‌شود و در موبایل به چینش عمودی تبدیل می‌شود. اطلاعات پایه، درس‌ها، min/required/max workload، اضافه‌کاری، محدودیت روزانه و grid حضور در همان detail قرار دارند. همین component هم در گام سوم برنامه‌ریزی و هم مقصد «دبیران» استفاده می‌شود.

## workspace برنامه هفتگی

- switch اصلی: «کلاس‌ها | دبیران | کل مدرسه»
- فیلترهای زمینه‌ای: پایه، رشته، کلاس یا دبیر
- grid روز × زنگ، با درس و دبیر در هر خانه
- کلیک خانه: edit drawer کوچک برای move/teacher/swap/delete
- خطا یا هشدار همان‌جا و کنار تغییر نمایش داده می‌شود
- ذخیره پیش‌نویس، انتشار، تاریخچه نسخه‌ها، PDF، Excel و چاپ در toolbar همین workspace هستند

گزینهٔ solver ابتدا فقط‌خواندنی نمایش داده می‌شود و با اقدام «آماده‌سازی برای اصلاح» یک snapshot کاری مستقل می‌سازد؛ بنابراین candidate اصلی تغییر نمی‌کند. نسخه‌های DRAFT/PUBLISHED/ARCHIVED از منوی تاریخچه در همین workspace دیده می‌شوند. snapshot تاریخی فقط‌خواندنی است و اقدام «ایجاد نسخهٔ کاری» آن را برای اصلاح fork می‌کند. انتشار نسخه قبلی همان سال را خودکار بایگانی می‌کند. خروجی‌های class/teacher/school نیز بدون route ناوبری مستقل از همین toolbar دریافت می‌شوند.

## قواعد جلوگیری از گسترش UI

- برای entityهای Grade، Major، Class، Subject و Curriculum route مستقل ساخته نمی‌شود.
- برای availability، workload، validation، conflict، run، version و export route مستقل ساخته نمی‌شود.
- route یا صفحه placeholder برای featureهای آینده ایجاد نمی‌شود.
- route هر مقصد هنگام Stage مربوط و همراه با حداقل جریان کاری واقعی ایجاد می‌شود؛ تا آن زمان آیتم پوسته غیرفعال است و به 404 هدایت نمی‌کند.
- notification، analytics، audit center و تنظیمات پیشرفته در UI فاز یک وجود ندارند.
